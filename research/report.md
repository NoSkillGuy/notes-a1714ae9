# Default caches explain the memory climb

A long-lived LanceDB process that keeps one connection can hold about **7 GiB** of cache — **6 GiB** for indexes and **1 GiB** for metadata — which is the same band as a pod that starts near **500 MB** and later sits at **7–7.5 GB** under an **8 GB** limit. Those figures are weighted budgets on the connection’s `Session`. The constructor records each budget as a weighted-entry limit and records that the budget is not a process RSS limit ([Lance session.rs](https://docs.rs/lance/latest/src/lance/session.rs.html)). Decoded table pages are not stored in either cache. No GitHub issue describes this pod: a table on a network volume or S3, opened per request, climbing across **10–15 days**. Two defects did let cache memory ignore its cap, and both are merged: an index-cache reference cycle when many datasets were opened ([lance#4680](https://github.com/lance-format/lance/pull/4680), merged 2025-09-10), and a metadata weigher that under-counted the largest file-metadata fields by about **100×**, so a nominal 1 GiB cap never evicted and a short random-read test gained **7,503 MB** before the fix ([commit 8ac0741](https://github.com/lance-format/lance/commit/8ac0741302052ca51e0ba01827d89744f2a62fe2), 2026-04-11). Other open tickets show resident memory still rising after the measured cache is inside its cap. Those are allocator retention, and a smaller cache leaves them in place. Read `session.size_bytes()` against RSS before changing anything. If the cache accounts for the climb, put an explicit byte budget on one shared `Session` and keep that session for the life of the pod. If the cache stays small while RSS moves, the remaining levers are the scan buffer and the glibc allocator.

## Default budgets already sum to 7 GiB

Lance keeps runtime state for a dataset on a `Session`. The session owns two caches, and `Session::default()` sizes them at `6 * 1024 * 1024 * 1024` bytes and `1024 * 1024 * 1024` bytes ([Lance dataset.rs](https://docs.rs/lance/latest/src/lance/dataset.rs.html), [Lance session.rs](https://docs.rs/lance/latest/src/lance/session.rs.html)). `lancedb.Session.default()` documents the same pair as **6 GB and 1 GB** ([LanceDB Python API](https://lancedb.github.io/lancedb/python/python/)). The index cache holds opened vector and scalar indexes. A B-tree search loads the index in pages of **4096 values**; bitmap search loads bitmaps one at a time. The metadata cache holds manifests, transactions, deletion vectors, row-id structures, index metadata, and per-file and per-column metadata. Keys are scoped by dataset URI, and several of them include the dataset version, so a new version is a new entry ([Lance performance guide](https://lance.org/guide/performance/)). `LanceCache` is the Rust wrapper that builds those keys and forwards them to the backend ([LanceCache](https://docs.rs/lance/latest/lance/cache/struct.LanceCache.html)). The Python `Session` constructor exposes the two byte sizes and hardcodes the object-store registry, so a Python pod cannot plug in a custom backend ([lancedb#3106](https://github.com/lancedb/lancedb/issues/3106)).

The object-store registry on that session caches store clients — HTTP pools, credentials, rate limiters — and holds them as weak references ([lance-io providers.rs](https://docs.rs/lance-io/latest/src/lance_io/object_store/providers.rs.html)). It does not cache file bytes. There is no separate data-page cache. Scan buffering is per scan: the default `io_buffer_size` is **2 GB**, described as enough for about 64 pages of typically **8–32 MB**, and it is a soft limit because a read cannot be smaller than one page. The guide’s upper bound for a scan is about `(2 * io_buffer_size) + (batch_size * num_compute_threads)` bytes, with a default batch of **8192** rows ([Lance performance guide](https://lance.org/guide/performance/)). That buffer is already larger than this pod’s **1.5 GB** request. It is a per-scan peak. It is the wrong shape for a floor that ratchets upward for two weeks after queries return.

The arithmetic lines up with the chart in either unit. **6 GiB + 1 GiB = 7 GiB**, which is **7.5 GB** in decimal units, the top of the reported band. Adding the **500 MB** starting footprint on top of a completely full budget lands near **8.0 GB**, which is the limit. Counted as binary gigabytes, **0.5 GiB + 7 GiB = 7.5 GiB**. The session docs also say the weight differs from RSS: policy weights can count a shared allocation once per entry, and `Session.size_bytes()` is a separate deep-size walk ([Lance performance guide](https://lance.org/guide/performance/), [Lance session.rs](https://docs.rs/lance/latest/src/lance/session.rs.html)). The defaults are large enough to consume this pod. They become the explanation only when `size_bytes()` moves with RSS.

Filling the budget requires the session to stay alive while queries touch more index pages and file metadata. A static table that is read through should approach the cap and stop, once the weigher is honest. The published docs disagree on the backend that enforces the cap. docs.rs `Session::new` constructs a `QuickCacheBackend`. The performance guide still calls both caches an LRU and also documents Moka, including `session.set_index_cache_capacity` and `session.set_metadata_cache_capacity`. Those setter names are absent from the docs.rs session source fetched for this research ([Lance session.rs](https://docs.rs/lance/latest/src/lance/session.rs.html), [Lance performance guide](https://lance.org/guide/performance/)). Byte sizes passed at construction exist on both generations. A later shrink depends on the installed build.

Entry-count knobs are a trap on older call sites. Since Lance **0.30.0** (2025-06-19) the count parameters are deprecated and converted at **20 MiB per index entry** and **10 MiB per metadata entry** ([Lance dataset.rs](https://docs.rs/lance/latest/src/lance/dataset.rs.html), [lance v0.30.0](https://github.com/lancedb/lance/releases/tag/v0.30.0)). The Python `open_table(..., index_cache_size=)` docstring still says the default is **256** entries. At 20 MiB each, 256 entries is **5 GiB**, close to the byte default, and only when that deprecated path is what actually runs. Omitting it uses the 6 GiB byte default. Setting either byte size to **0** disables that tier ([Lance dataset builder](https://docs.rs/lance/latest/src/lance/dataset/builder.rs.html)).

## Per-request opens leave the connection session resident

LanceDB does not give each `open_table` its own cache. `connect()` creates one `Session` unless the caller passes one, stores it on the database, and clones that `Arc` into every open ([lancedb listing.rs](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)). Once a session is attached, the dataset builder ignores `with_index_cache_size` and `with_metadata_cache_size` and uses the session’s budgets ([Lance dataset builder](https://docs.rs/lance/latest/src/lance/dataset/builder.rs.html)). A pod that connects once and opens the table on each request therefore deposits every index load and every file-metadata read into the same session, and dropping the table object leaves that session in place. Python, Node, and Rust share this model. None of them installs a process-global cache. A second `connect()` without an explicit session builds a second session and a second object-store registry ([LanceDB Python API](https://lancedb.github.io/lancedb/python/python/), [lancedb#2530](https://github.com/lancedb/lancedb/pull/2530)).

`AsyncTable.close()` and garbage collection free index data that the table itself owns. The JavaScript and Python async docs say so, and they say `close()` frees it eagerly ([LanceDB JS Table](https://lancedb.github.io/lancedb/js/classes/Table/), [table.py](https://github.com/lancedb/lancedb/blob/8ae4f42f/python/python/lancedb/table.py)). The connection session is a different object. Closing one table leaves it in place. At the commit that was read, the synchronous Python `Table` wrapper does not define `close()`, so a sync `open_table` drops its handle when the garbage collector runs. The async connection docs say embedded connections “do not currently hold any open resources,” and they also say one connection is meant to last for the life of the process ([LanceDB Python API](https://lancedb.github.io/lancedb/python/python/)). Dropping the connection drops the session only when the caller is not still holding that `Session`. The `memory://` URI is a different case: closing the last handle deletes the table ([lancedb#2247](https://github.com/lancedb/lancedb/issues/2247)). Passing an empty `storage_options` map is another footgun on the per-request path: it builds a new object store that is dropped when Python collects the table, instead of reusing the connection’s registry ([lancedb listing.rs](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)).

Maintainers want the sharing. The performance guide says the caches are not shared between tables by default and tells applications to keep one table, or one session, for the whole process ([Lance performance guide](https://lance.org/guide/performance/)). Weston Pace described a fresh cache per table instance as something that “can lead to memory issues,” and asked for one shared cache ([lancedb#1336](https://github.com/lancedb/lancedb/issues/1336)). The shared session is that fix, and its default size is the 7 GiB above. On an 8 GB limit the recommended shape and the default numbers conflict: keep one session, and set its budget, because the default budget is the pod.

A network volume and S3 use those same session caches. Weston Pace wrote that caching and buffering do not work very differently between local files and S3 ([lancedb#2468](https://github.com/lancedb/lancedb/issues/2468)). What changes is the store client and the I/O defaults. A filesystem path, including a mounted network volume, is a local store: **8** I/O threads, a **4 KB** `block_size`, and no cloud rate limiter. An `s3://` URI uses **64** I/O threads, a **64 KB** block size, and an AIMD limiter aimed at in-region bandwidth ([Lance performance guide](https://lance.org/guide/performance/), [object store guide](https://lance.org/guide/object_store/)). No issue or doc in this research mentions NFS, EFS, or a Kubernetes network volume. The local-store path still fills the index and metadata caches.

S3 adds two retention paths that a filesystem mount does not. The registry key includes storage options, so refreshed `access_key_id`, `secret_access_key`, and session tokens insert new entries ([lance#5658](https://github.com/lance-format/lance/issues/5658)). Current source keeps those stores as weak references and sweeps dead entries once the cache holds `object_store_cache_prune_threshold` of them, default **64**, with **0** disabling the sweep ([object store guide](https://lance.org/guide/object_store/)). Separately, once a vector index is cached, later opens reuse readers bound to the `ObjectStore` from insertion time. On `lance` 8.0.0 the Moka backend had no time-to-live and no idle timeout, a stale credential binding was observed for at least **12 hours**, and the reporter’s recovery was to restart the process that owned the session ([lance#7904](https://github.com/lance-format/lance/issues/7904)). That session was the application’s singleton, not a hidden Lance global.

Before the 2025-09-10 fix, the per-request pattern leaked even when each open used a private session. Loading an index stored a strong reference from the index back to the index cache, so dropping the dataset did not free the cache “if many datasets were opened over time” ([lance#4680](https://github.com/lance-format/lance/pull/4680)). The first release tag that contains that commit was not identified. The merge is after Lance 0.30.0 (2025-06-19) and after Python and TypeScript sessions shipped (2025-07-24). A practitioner note, not a maintainer, says that on `lancedb==0.25.0` opening and closing a connection per use leaked, and that the author switched to one long-lived connection while still calling `open_table()` per request ([sprytnyk.dev](https://sprytnyk.dev/posts/running-lancedb-in-production/)). If each request instead calls `connect` and then drops every reference to the connection and the session, current code frees both caches with that session, on a binary that includes the weak-reference fix. A monotonic chart on that pattern is an older binary still holding the cycle, or glibc keeping the per-request peak.

## GitHub shows a cycle, a bad weigher, and RSS that ignores the cache

No issue text contains “10–15 days,” “7–7.5 GB,” or this pod’s request and limit. The reports that match a long-lived process fall into three mechanisms.

The metadata weigher is the one with a measured multi-gigabyte climb. `CachedFileMetadata::DeepSizeOf` omitted `column_metadatas` and `column_infos`, the two largest fields. True size was hundreds of kilobytes and the reported weight was about 1 KB, roughly a **100×** under-count, so Moka never reached the 1 GB limit and entries accumulated indefinitely. On a **221-million-row** dataset, 30 iterations of a random 64-row `take()` grew RSS by **7,503 MB** before the fix, about **250 MB** per iteration with no plateau, and by **535 MB** after, about **18 MB** per iteration, plateauing near **500 MB** ([commit 8ac0741](https://github.com/lance-format/lance/commit/8ac0741302052ca51e0ba01827d89744f2a62fe2)). [lance#6480](https://github.com/lance-format/lance/pull/6480) merged the same day and includes those two fields in the weight. Whether QuickCache, the backend in current docs.rs, weighs entries with that same trait was not re-checked. The under-count lived in `DeepSizeOf`, which any weigher based on that trait inherits. A workload that touches new files slowly spreads that unbounded accumulation across days. A build with the fix should plateau.

The reference cycle is the one that matches “opened per request” on an older build. Each opened dataset that loaded an index kept its index cache alive after the dataset was dropped ([lance#4680](https://github.com/lance-format/lance/pull/4680)). Weak references replaced the strong ones. That fix leaves the RSS of one table that stays open on one session unchanged. It stops a new cache from surviving every request.

Versioned keys sit between those bugs and ordinary capacity. Manifest, transaction, deletion-file, and row-id keys include the version ([Lance performance guide](https://lance.org/guide/performance/)). A Ray Serve replica on S3, lance 4.0.0, one shared session, an index-cache budget of **150 GB**, a metadata-cache budget of **2 GB**, a 30-second `read_consistency_interval`, and daily index rebuilds was reported to accumulate memory until OOM at a low query rate ([lance#7508](https://github.com/lance-format/lance/issues/7508)). The reporter’s mechanism — new UUID or version keys, `checkout_latest` leaving the cache in place, and the under-counted weigher — was not confirmed by a maintainer. The only maintainer comment on that issue is about an FTS length error and an upgrade past 4.0.0. The issue was closed on 2026-08-23 without a statement that the memory claim was reproduced. An unmerged pull request would evict version-scoped index and metadata entries when cleanup deletes their files. Until that lands, eviction is the byte budget alone ([lance#7718](https://github.com/lance-format/lance/pull/7718)). The same class of long-lived session also pinned one file descriptor per optimized legacy index until [lance#10534](https://github.com/lance-format/lance/pull/10534) (merged 2026-10-31, closes [lance#9934](https://github.com/lance-format/lance/issues/9934)). That ticket is descriptors. Capping `metadata_cache_size_bytes` is what plateaued the descriptor count.

The third mechanism is resident-set growth with the cache already inside its cap. [lance#6219](https://github.com/lance-format/lance/issues/6219) (open, updated 2026-08-07) ran concurrent vector search against Azure with both caches capped at **100 MB**. Logged RSS went from **0.03 GB** to about **1.04 GB** within a few minutes while the session cache stayed near **100–140 MB**. `malloc_trim` every 30 seconds returned roughly **52–68 MB**, and RSS resumed climbing. Xuanwo could not reproduce it on AWS, wrote that RSS came back after trim there, and asked whether the remainder was Azure-specific. The ticket has no cause and no fix. [lance#7242](https://github.com/lance-format/lance/issues/7242) (open) is a long-lived `merge_insert` loop on pylance 7.0.0: about **5–7 MB** RSS per iteration, and **42 GB** after about 1400 flushes. After 50 iterations `mallinfo2` showed `in_use` near **29 MB** and `free_not_returned` at **395 MB**. `MALLOC_ARENA_MAX=2` held RSS near **75–83 MB**. Will Jones has not accepted glibc arenas as the cause, and the mimalloc pull request was not merged ([lance#7245](https://github.com/lance-format/lance/pull/7245)). [lancedb#1592](https://github.com/lancedb/lancedb/issues/1592) (open since 2024) is the maintainer’s own measurement of the same allocator behavior on one search: **1.56 GB** of system bytes versus **29 MB** in use, `malloc_trim` recovered about half, and jemalloc via `LD_PRELOAD` ended near **250 MB**. Weston Pace called that not a leak, and said returning the memory had not been a priority because a process that needed 2 GB would likely need 2 GB again. [lance#3798](https://github.com/lance-format/lance/issues/3798) says merge-insert memory accumulates and is still open, with no RSS series.

The other “leak” titles are one-shot high-water marks. The S3 one that matters for an 8 GB pod is [lancedb#2468](https://github.com/lancedb/lancedb/issues/2468): a cosine search with a prefilter on an unindexed table of about 2 GB and 2 million rows exceeded **16 GB**, and later searches in the same session sat at that watermark. [lancedb#3805](https://github.com/lancedb/lancedb/pull/3805) (merged 2026-08-26) fixed it by sharing one scan across a batch of query vectors. The reporter was already reusing a session. A POSIX S3 mount used much less RAM in that thread. On this pod that spike crosses the 8 GB limit on the first batch. It is a different shape from a two-week ramp. Optimize and compaction OOMs track data size inside one job, and each optimize in the Kubernetes report was a new pod ([lance#4561](https://github.com/lance-format/lance/issues/4561), [lancedb#2325](https://github.com/lancedb/lancedb/issues/2325)).

## Bound the session, then see whether RSS still moves

The measurement that separates these mechanisms is already on the session. `dataset.session().size_bytes()` is the deep size of the caches. The performance guide also documents `cache_diagnostics()` with `backend.size_bytes` and `backend.capacity_bytes` ([Lance performance guide](https://lance.org/guide/performance/)). If that size climbs toward the 6 GiB and 1 GiB budgets in step with RSS, the pod is doing what the defaults allow, or it is still on the pre-2026-04-11 weigher. If `size_bytes` stays near a small cap while RSS follows the 10-day curve, the pod matches [lance#6219](https://github.com/lance-format/lance/issues/6219) and [lance#7242](https://github.com/lance-format/lance/issues/7242), and a tighter cache will leave the resident set where it is.

Size the session at `connect`, not on `open_table`. Table-level cache configuration is deprecated, and a session passed into the builder replaces the builder’s sizes ([lancedb#2530](https://github.com/lancedb/lancedb/pull/2530), [Lance dataset builder](https://docs.rs/lance/latest/src/lance/dataset/builder.rs.html)). Upstream publishes no container-sized default. The numbers below are a starting budget for this 8 GB limit: **1 GiB** of index cache and **256 MiB** of metadata, against a **500 MB** baseline, leave room for a scan. Raise them only if diagnostics show the cache thrashing and queries are waiting on the network volume or S3. A smaller index budget means more index-page reads from storage. A maintainer has said that a larger index cache is what cuts those reads ([lance#3722](https://github.com/lance-format/lance/issues/3722)).

```python
session = lancedb.Session(
    index_cache_size_bytes=1024 * 1024 * 1024,
    metadata_cache_size_bytes=256 * 1024 * 1024,
)
db = lancedb.connect(uri, session=session)
```

Zero disables a tier. Shrinking capacity later is documented as evicting entries without dropping the session, on builds that expose `set_index_cache_capacity` and `set_metadata_cache_capacity` ([Lance performance guide](https://lance.org/guide/performance/)). Confirm those methods on the installed package before relying on them. Spark’s `LANCE_INDEX_CACHE_SIZE` and `LANCE_METADATA_CACHE_SIZE` were not found as readers in the core library ([Spark config](https://lance.org/integrations/spark/config/)). Setting them on this pod leaves the embedded session unchanged.

For the scan path, the guide’s starting point on a bandwidth-constrained remote store is `LANCE_IO_THREADS=8`, `fragment_readahead=1`, `batch_readahead=2`, and `io_buffer_size=64 * 1024 * 1024` ([Lance performance guide](https://lance.org/guide/performance/)). `LANCE_DEFAULT_IO_BUFFER_SIZE` overrides the 2 GB v2 default ([scanner.rs](https://docs.rs/lance/latest/src/lance/dataset/scanner.rs.html)). Thread pools are created at startup, so `LANCE_IO_THREADS` and `LANCE_CPU_THREADS` have to be set before Lance is imported. A mounted network volume already follows the local defaults of 8 threads and 4 KB blocks. An `s3://` URI follows the cloud defaults, and 64 in-flight cloud reads plus a 2 GB soft buffer are sized for a large machine. `LANCE_READ_CACHE_REPETITION_INDEX=false` turns off repetition-index caching for large string and binary columns. That cache is enabled by default and is charged to the metadata cache, about **1.6 MiB per 200,000 rows** in the maintainer’s note ([lance#5981](https://github.com/lance-format/lance/pull/5981)). `object_store_cache_prune_threshold` bounds how many dead store clients a session keeps.

Allocator retention has no Lance API. On the merge-insert loop, `MALLOC_ARENA_MAX=2` is the setting that kept RSS flat in the reporter’s `mallinfo2` run ([lance#7242](https://github.com/lance-format/lance/issues/7242)). `malloc_trim(0)` returned tens of megabytes in [lance#6219](https://github.com/lance-format/lance/issues/6219) and about half the heap in [lancedb#1592](https://github.com/lancedb/lancedb/issues/1592), and the floor kept rising in the Azure log. jemalloc is what Weston Pace used to land near 250 MB on that issue. A switch to mimalloc inside pylance was not merged, and the jemalloc investigation was closed not-planned ([lance#1372](https://github.com/lance-format/lance/issues/1372)). `GLIBC_TUNABLES=glibc.malloc.hugetlb=1` is a decode-speed option the guide says can raise RSS ([Lance performance guide](https://lance.org/guide/performance/)). `LANCE_MEM_POOL_SIZE` defaults to **100 MiB** and is a spill ceiling inside merge insert ([lancedb#2711](https://github.com/lancedb/lancedb/issues/2711)).

| Knob | Default | What it bounds |
| --- | --- | --- |
| `Session(index_cache_size_bytes=)` | 6 GiB | Weighted index-cache budget. `0` disables the tier. Set it on the session passed to `connect`. |
| `Session(metadata_cache_size_bytes=)` | 1 GiB | Weighted metadata-cache budget. `0` disables the tier. |
| `io_buffer_size`, `LANCE_DEFAULT_IO_BUFFER_SIZE` | 2 GB | Soft per-scan I/O buffer. The guide’s constrained starting point is 64 MiB. |
| `LANCE_IO_THREADS` | 8 local, 64 cloud | Concurrent storage requests. Set before import. |
| `LANCE_READ_CACHE_REPETITION_INDEX` | enabled | `false` stops repetition-index entries in the metadata cache. |
| `object_store_cache_prune_threshold` | 64 stores | How many idle object-store clients one session keeps. |
| `MALLOC_ARENA_MAX` | glibc default | `2` held RSS flat in the merge-insert arena report. This is glibc, not a Lance setting. |

The upgrade that matches the cache bugs is a lance build containing the 2025-09-10 weak-reference fix and the 2026-04-11 weigher fix. This research did not map those commits to release tags, so a version number alone does not show that either fix is present. No maintainer has said the process must be restarted to release a healthy cache. Restart is what cleared the credential-stuck index reader in [lance#7904](https://github.com/lance-format/lance/issues/7904).

## Conclusion

The 10–15 day slope is what separates a cache that has finished filling from one that is still accepting keys. On an honest weigher, a static table moves `size_bytes` while distinct index pages and file metadata are touched for the first time, then sits still. That is what the reporter on [lance#3128](https://github.com/lance-format/lance/issues/3128) already recorded when the same rows were read again. A curve that is still rising in the second week means new keys are still arriving — new dataset versions, new index UUIDs after optimize, or a dataset object retained on every request by a build older than the weak-reference fix — or the allocator is keeping pages the cache has already released. A smaller session budget stops the key accumulation. Allocator retention continues under any cache budget, which is why the `size_bytes` reading comes before the config change.

Lance’s maintainers have treated a high-water mark as acceptable, because the next query in a long-running process is likely to need the memory again. That judgment is explicit on [lancedb#1592](https://github.com/lancedb/lancedb/issues/1592), and an 8 GB cgroup cannot afford it. The defaults were chosen for a machine that can spare 7 GiB of cache and a 2 GB scan buffer. This pod’s 1.5 GB request never bounded the process. The limit did. The running binary still has to be checked against the 2025-09-10 and 2026-04-11 merge dates, because those commits were not mapped to release tags, and the open RSS tickets remain unreproduced on AWS and unfixed.
