Search date: 2026-11-25. Primary repos: [lancedb/lancedb](https://github.com/lancedb/lancedb) and [lance-format/lance](https://github.com/lance-format/lance). `lancedb/lance` now resolves to `lance-format/lance` (same issue numbers). No issue states the pod shape in the assignment (network volume or S3, table opened per request, 1.5 GB request / 8 GB limit, ~500 MB rising to 7–7.5 GB over 10–15 days). Where a report is only partly similar, that is marked as an inference.

## Which issues report RSS or heap climbing over hours, days, or weeks and not returning to baseline?

### Takeaway
A few open reports describe RSS that keeps rising inside one long-lived process while measured cache size or live heap stays flat. Most “memory leak” tickets are a single ingest, index build, or optimize whose peak tracks data size or concurrency, measured in minutes or one job, and they do not claim a multi-day baseline that never returns.

### Takeaway

### Inferences
- Opening a table per request matches the failure mode described in #4680 only if each open loads an index into a cache that then fails to drop. The PR does not mention requests, pods, or remote storage.
- A process that keeps one session can fill the default 6 GiB index cache plus 1 GiB metadata cache. That is large enough to land near 7 GB on an 8 GB limit if those caches fill. That is a capacity fact about defaults, not evidence that any particular pod is filling those caches. #6219 is the counterexample in which RSS climbed while the cache was inside a 200 MB cap.
- GCS, NFS, and “network volume” do not appear in the leak threads that were fetched. Azure is only #6219. S3 is #2468, #4561, #7508, and the 2023 explanation #80.

### Gaps
- No issue states “open the table on every request.”
- No NFS or network-volume memory issue was found.
- No GCS-specific RSS issue was found (a GCS search hit unrelated titles).
- No Node.js server leak issue was found.
- The SSL-certificate reload leak is only wjones127’s comment on #2468. The production fix and the missing binding were not tied to a PR in this search.

## What did maintainers identify as the cause, and was it fixed?

### Takeaway
Maintainers have named four different mechanisms: an index-cache reference cycle when many datasets are opened, I/O schedulers that were not shut down, batch S3 searches that ran one full scan per query vector, and FTS merge memory that scaled with the build. The open long-running RSS tickets (#6219, #7242, #3798) do not have a merged fix. Allocator retention was demonstrated by a maintainer in 2024 and treated as out of scope.

### Cited Findings

Confirmed by a maintainer or by the fixing PR, and merged:

- Many datasets opened over time. [lance#4680](https://github.com/lance-format/lance/pull/4680) (author wkalt, merged 2025-09-10): index objects held a strong reference to the index cache, so the cache was not freed when the dataset was dropped. Fix: weak references. No release tag was looked up. — [lance#4680](https://github.com/lance-format/lance/pull/4680)
- Read-path schedulers, 2024. On [lance#3128](https://github.com/lance-format/lance/issues/3128), westonpace said the drop from pylance 0.18.0 to 0.19.2 matches commit [`47eb00ef`](https://github.com/lancedb/lance/commit/47eb00ef615e1f4776aadd996c115debfb3387a3), which shut down file and scan I/O scheduler loops that were never deallocated. He also said the largest bytehound allocations were in `moka`, which might be a moka bug, expected background-thread behavior, or the cache growing on each call, and asked for `ds.session().size_bytes()`. Reporter’s last note: cache grows slowly when traversing different rows; cache size does not change when re-reading the same data. Issue closed not-planned the same day (2024-11-29). wjones127 had said he was not aware of a leak and that the metadata cache filling was one explanation. — [lance#3128](https://github.com/lance-format/lance/issues/3128)
- S3 batch vector search spike. [lancedb#3805](https://github.com/lancedb/lancedb/pull/3805) merged 2026-08-26, closes #2468. PR: LanceDB expanded each vector in a batch into its own scan and joined them with `UnionExec`, so ten vectors on an unindexed S3 table ran ten concurrent full scans. Fix uses Lance’s native batch KNN path so one flat scan serves the batch. Nonzero offset still uses the old plan. This is a different cause from the SSL-certificate hypothesis wjones127 offered on 2025-06-26, which the thread never confirmed. — [lancedb#3805](https://github.com/lancedb/lancedb/pull/3805), [lancedb#2468](https://github.com/lancedb/lancedb/issues/2468)
- Arrow buffers retained across `Table.add` until GC. wjones127 on #2512 (2025-07-17): if it does not reproduce in Lance, the Python preprocessing generators in `Table.add` are the suspect. [lancedb#3860](https://github.com/lancedb/lancedb/pull/3860) merged 2026-08-06, closes #2512. PR: the historical path held a high allocator RSS on wide IPC batches; the current Scannable writer releases each input buffer when `add()` returns; a regression test checks live buffer release without cyclic GC. Comment on the issue, 2026-08-05, lancedb-gatefixer: on commit `c7ea91f` / Python 0.37.1b0, RSS was about 1.18–1.19 GiB above baseline with or without `gc.collect()`; 0.24.1 had a higher high-water mark and `gc.collect()` did not produce the reported drop. Xuanwo closed it as already fixed on 0.37.1b0. #2693 was closed as a duplicate before that fix. — [lancedb#2512](https://github.com/lancedb/lancedb/issues/2512), [lancedb#3860](https://github.com/lancedb/lancedb/pull/3860), [lancedb#2693](https://github.com/lancedb/lancedb/issues/2693)
- FTS index-build memory. [lancedb#3796](https://github.com/lancedb/lancedb/pull/3796) merged 2026-08-21, closes #2923. Reporter workaround before the fix: set `metadata_cache_size_bytes` (1 MB plateaued near 216 descriptors; 4 MB plateaued at 814; `None` uses the 1 GB default and did not plateau). Capping only `index_cache_size_bytes` did not. — [lance#10534](https://github.com/lance-format/lance/pull/10534), [lance#9934](https://github.com/lance-format/lance/issues/9934)

### Inferences
- For a long-running reader, the merged fixes that change lifetime behavior are #4680 (drop caches when datasets are dropped) and the 0.19 scheduler shutdown. They do not cap RSS of one table that stays open.
- For a long-running writer, #10534 stops descriptor leaks from cached legacy indexes; #7718, which would drop version-scoped cache entries after cleanup, is not merged. #7245, which would change the Python allocator, is not merged.
- The S3 “memory leak” that was actually fixed (#2468 via #3805) was concurrent full scans of an unindexed table during a batch query, which fits a spike to a high watermark, not a 10-day ramp.

## Which reports are confirmed leaks versus cache growth, fragmentation, or unreproducible?

### Takeaway
The cases with a code-level cause and a merged fix are the index-cache reference cycle (#4680), the pre-0.19 I/O scheduler loops (#3128, partial), the S3 batch-scan amplification (#2468), retained Arrow inputs on `add` (#2512), FTS build and lindera query peaks (#2923, #10274), and index-cache file descriptors (#9934). The multi-operation RSS climbs that are still open are either unreproduced (#6219 on AWS, #3798) or measured as glibc retaining freed memory (#7242), which a maintainer has not accepted as a Lance leak.

### Cited Findings

Confirmed leak (memory or descriptor still referenced after the operation), with a merged fix:

- Index cache cycle when many datasets are opened: [lance#4680](https://github.com/lance-format/lance/pull/4680), merged 2025-09-10.
- I/O scheduler loops not shut down, visible as much larger growth on pylance 0.18.0 than 0.19.2: westonpace on [lance#3128](https://github.com/lance-format/lance/issues/3128), commit [`47eb00ef`](https://github.com/lancedb/lance/commit/47eb00ef615e1f4776aadd996c115debfb3387a3). The same issue’s leftover growth was not confirmed as a leak.
- Open file descriptor per optimized index version: [lance#9934](https://github.com/lance-format/lance/issues/9934) / [lance#10534](https://github.com/lance-format/lance/pull/10534), merged 2026-10-31. This is descriptors, not an RSS measurement.
- Live Arrow buffer retained until Python GC, historical `Table.add` path: [lancedb#2512](https://github.com/lancedb/lancedb/issues/2512), treated as fixed by the Scannable writer and covered by [lancedb#3860](https://github.com/lancedb/lancedb/pull/3860). The PR itself separates “live input retention” from “allocator high-water.”

Confirmed high peak or retained working set during one operation, not an unbounded process leak:

### Inferences
- A pod that opens a new table per request and drops it can still have been affected by #4680 until that weak-reference fix is in the deployed lance. After that fix, the same pattern should release the index cache unless something else retains the dataset or the session.
- A pod that keeps one connection can sit on the default 6 GiB + 1 GiB caches without any of the confirmed leaks. #6219 shows that a climb past the cache cap is a separate, still-open report, and it was on Azure with concurrent search, not on a quiet request path.
- The strongest quantitative “RSS up, live heap flat” evidence is #7242 (`mallinfo2`) and #1592 (`malloc_stats`). Both are allocator retention. Only #7242 is a long loop that would hit an 8 GB limit if the process kept doing `merge_insert`. It is a writer workload on local disk in the repro, pylance 7.0.0, and the proposed mimalloc change is not merged.
- Nothing fetched confirms a leak that requires S3 or a network volume specifically, except the unlinked SSL-reload comment. The fixed S3 report (#2468) was scan amplification. The S3 optimize OOM (#4561) tracked data size inside one cron pod.

### Gaps
- No maintainer has published a heap profile for #6219, so “fragmentation plus an unknown remainder” is a reading of the trim log, not their conclusion.
- #7242’s `in_use` column is the reporter’s measurement. wjones127 asked for an allocator-swap run and a batch-size run; the fetched thread does not include his acceptance of those results.
- Whether lance 4.0.0 (the #7508 version) already contained #6480 or #6563 was not checked against tags.
- No discussion thread was found that adds a maintainer diagnosis beyond the issues and PRs above.
