# Lance and LanceDB in-memory cache behavior

Scope: which in-process caches hold table metadata, indexes, and data pages; whether they survive across requests in a long-lived process; and whether they are released when a table or connection is dropped. Sources are current Lance docs and published crate source unless a finding is explicitly marked as removed or version-specific. Two current-facing sources disagree on the cache backend and on a few Session methods; that disagreement is called out below rather than resolved.

The user context used only for inference: a table on a network volume or S3, opened per request in a long-lived pod, RSS about 500 MB at start and 7–7.5 GB after 10–15 days, pod limit 8 GB.

## What do LanceCache, the object-store cache, the index cache, the metadata cache, and session or runtime caches store, and what are their defaults and eviction policies?

### Takeaway

A Lance `Session` is the runtime object that owns two byte-budgeted caches: an index cache (default `6 * 1024 * 1024 * 1024` bytes, 6 GiB) and a metadata cache (default `1024 * 1024 * 1024` bytes, 1 GiB). Those budgets are weighted capacities, not preallocated RSS and not a hard process limit. `LanceCache` is the typed wrapper around the backend. The object-store “cache” stores live `ObjectStore` clients, not file bytes. Decoded table data pages are not kept in either session cache; scan buffering is separate and per scan.

### Cited Findings

#### Session, index cache, and metadata cache

- A `Session` “holds the runtime state for a Dataset.” One is created automatically when a dataset is opened. Passing a session into the dataset builder shares that state across datasets. The session contains an index cache (“cache opened indices and will cache index data”) and a metadata cache (“a variety of dataset metadata”). — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html)
- `Session::new(index_cache_size, metadata_cache_size, store_registry)` documents `index_cache_size` as “the weighted-entry budget of the index cache” and says “This is not an RSS limit: active queries and in-progress loaders can retain memory in addition to resident cache entries.” The same comment says the budget “is not a process RSS limit.” — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html)
- `Session::default()` calls `Session::new(DEFAULT_INDEX_CACHE_SIZE, DEFAULT_METADATA_CACHE_SIZE, Arc::new(ObjectStoreRegistry::default()))`. — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html)
- `DEFAULT_INDEX_CACHE_SIZE` is `6 * 1024 * 1024 * 1024`. The adjacent comment says “We default to 6GB for the index cache.” `ReadParams` documents that field as “The default is 6 GiB.” `DEFAULT_METADATA_CACHE_SIZE` is `1024 * 1024 * 1024`. The comment says column metadata “can be like 40MB” and “The default is 1 GiB.” Setting either cache size to zero disables that cache. — [docs.rs `lance` `dataset.rs`](https://docs.rs/lance/latest/src/lance/dataset.rs.html)
- The performance guide says the metadata cache “holds various pieces of metadata such as file metadata, dataset manifests, etc.,” is “an LRU cache that is sized by bytes,” and defaults to 1 GiB. It is “not shared between tables by default.” Keys are scoped to the dataset URI. Stored items:

  | Item | Key | What is stored |
  | --- | --- | --- |
  | Dataset manifests | dataset URI, version, and etag | manifest |
  | Transactions | dataset URI, version | transaction |
  | Deletion files | dataset URI, fragment id, version, id, file type | deletion vector |
  | Row id mask | dataset URI, version | row id sequence |
  | Row id index | dataset URI, version | row id index |
  | Row id sequence | dataset URI, fragment id, row id meta | row id sequence for a fragment |
  | Index metadata | dataset URI, version | index metadata |
  | Index details (only very old indexes whose details are not in the manifest) | dataset URI, index uuid | index details |
  | File global meta | dataset URI, file path | global metadata for a file |
  | File column meta | dataset URI, file path, column index | “the search cache for a column” |

  — [Lance performance guide](https://lance.org/guide/performance/)
- The same guide says the index cache “caches vector and scalar indices in memory,” is configured with `index_cache_size_bytes`, “is an LRU cached that is sized by bytes,” and defaults to 6 GiB. It is “not shared between tables” unless the application shares a table or a session. B-tree index search loads the index into the index cache in pages of 4096 values. Bitmap search loads bitmaps into the session cache individually. — [Lance performance guide](https://lance.org/guide/performance/)
- `index_cache_size` and `metadata_cache_size`, specified as entry counts, have been deprecated since 0.30.0. The compatibility setters multiply entry counts by an assumed size: 20 MiB per index entry (`20 * 1024 * 1024`) and 10 MiB per metadata entry (`10 * 1024 * 1024`). Lance 0.30.0 was published on 2025-06-19 and lists “move file metadata cache to bytes capacity” as a breaking change. — [docs.rs `lance` `dataset.rs`](https://docs.rs/lance/latest/src/lance/dataset.rs.html); [lance v0.30.0](https://github.com/lancedb/lance/releases/tag/v0.30.0); [PR 3949](https://github.com/lance-format/lance/pull/3949)
- LanceDB’s current `OpenTableBuilder::index_cache_size` doc comment still says “The default value is 256” and that an entry is one IVF partition, or the entire B-tree. The Python `open_table` parameter of the same name is documented as deprecated in favor of session-level cache configuration, with the same IVF / B-tree entry meanings. In current `ListingDatabase::open_table`, that entry count is applied only when the caller set it and did not pass `lance_read_params`; the connection session is then attached with `read_params.session(self.session.clone())`. — [lancedb `connection.rs`](https://github.com/lancedb/lancedb/blob/main/rust/lancedb/src/connection.rs); [LanceDB Python API](https://lancedb.github.io/lancedb/python/python/); [docs.rs `lancedb` `listing.rs`](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)
- Index-cache sub-caches are keyed with the dataset URI and index UUID as a prefix, plus a fragment-reuse index prefix when one exists. Metadata-cache sub-caches are keyed with the dataset URI as a prefix. — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html)
- `Session::size_bytes()` is a deep-size walk of the caches, not the policy weight. `approx_num_items()` sums approximate index-cache items, metadata-cache items, and index extensions. The performance guide says policy `size_bytes` / `capacity_bytes` “include key accounting and can count a shared allocation for each entry that references it” and “are different from the deep-size estimate returned by `Session.size_bytes()` and from process RSS.” — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html); [Lance performance guide](https://lance.org/guide/performance/)

#### LanceCache and the backend (current source vs guide vs older releases)

- `LanceCache` is “a typed cache wrapper that handles key construction and type safety” and “delegates to a `CacheBackend`.” — [docs.rs `LanceCache`](https://docs.rs/lance/latest/lance/cache/struct.LanceCache.html)
- In the `session.rs` source published on docs.rs latest, `Session::new` builds both tiers with `QuickCacheBackend`. The index tier uses `QuickCacheShardPolicy::Single` because “Automatic index caches favor one shared budget because they commonly hold a small number of large, unequal partition entries.” The metadata tier uses `QuickCacheShardPolicy::Recommended`. `CacheSpec::Size` uses that same in-memory backend; `CacheSpec::Backend` accepts a caller-supplied backend. The file’s example plugs in `build_from_uri("moka://?capacity=1048576")`. — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html)
- The performance guide still describes both default caches as LRU. It also documents Quick and Moka as built-in backends, `session.set_index_cache_capacity(...)` and `session.set_metadata_cache_capacity(...)` (shrinking “evicts entries as needed”), and `dataset.session().cache_diagnostics()`. It says standard Moka does not report size-removal metrics unless enabled with `moka://?capacity=<bytes>&size_removal_metrics=true` or `MokaCacheBackend::builder(capacity).with_size_removal_metrics()`. A zero-capacity cache reports `enabled=False`. — [Lance performance guide](https://lance.org/guide/performance/)
- That `set_index_cache_capacity` / `cache_diagnostics` API is not present in the docs.rs latest `session.rs` source fetched for this research. That source exposes `size_bytes`, `approx_num_items`, `metadata_cache_stats`, and `index_cache_stats`. — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html); contradicted in part by [Lance performance guide](https://lance.org/guide/performance/)
- Version-specific: a commit on 2026-04-11 states “`LanceCache` uses moka with a weighted capacity of 1 GB (`DEFAULT_METADATA_CACHE_SIZE`).” Issue 7904 (opened 2026-07-22, reporter’s crate `lance` 8.0.0) shows `MokaCacheBackend::with_capacity` building a `moka::future::Cache` with `max_capacity` and a weigher on `size_bytes`, and states that no `time_to_live` or `time_to_idle` is configured, so entries leave only by capacity eviction or explicit clear. — [commit 8ac0741](https://github.com/lance-format/lance/commit/8ac0741302052ca51e0ba01827d89744f2a62fe2); [issue 7904](https://github.com/lance-format/lance/issues/7904)
- The published docs.rs session (QuickCache) and the April–July 2026 Moka reports are different generations. The guide’s “LRU” sentence does not match the QuickCache constructor in the published session source.

#### Object-store cache (clients, not file bytes)

- `ObjectStoreRegistry` “caches object stores that are currently in use” and “holds weak references to the object stores, so they are not held onto.” A dead weak entry is removed on the next `active_stores()` or when `get_store()` looks up that key and `upgrade()` fails. The map key includes the store path and `ObjectStoreParams`. — [docs.rs `lance-io` `providers.rs`](https://docs.rs/lance-io/latest/src/lance_io/object_store/providers.rs.html)
- Since a breaking change merged 2025-04-18, the registry lives on the `Session`. The PR removed `object_store_registry` from `ReadParams` and `WriteParams`. Its summary says the registry cache lets datasets that share a session reuse object stores when their parameters match. — [PR 3689](https://github.com/lancedb/lance/pull/3689); [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html)
- Storage option `object_store_cache_prune_threshold`: “Smallest number of cached object stores at which a session's object store cache sweeps out entries for stores that are no longer in use. Default, `64`; `0` disables the sweep.” The last value seen applies to every dataset on that session. The doc says this matters when one session opens many tables with distinct storage options, such as per-table credentials. — [object store guide](https://github.com/lance-format/lance/blob/main/docs/src/guide/object_store.md)
- `block_size` is not a cache capacity. It is the gap below which two reads of one file are merged into one request. Default `4096` for local files and `65536` for object stores. Cloud stores are wrapped with an AIMD rate limiter on HTTP 429/503. `LANCE_PROCESS_IO_THREADS_LIMIT` is described as replaced by that limiter. — [object store guide](https://github.com/lance-format/lance/blob/main/docs/src/guide/object_store.md); [Lance performance guide](https://lance.org/guide/performance/)
- `new_store` is documented as building a store “without consulting or populating the cache,” and callers “should retain the returned Arc for as long as they want to reuse provider-local state such as HTTP clients and rate limiters.” — [docs.rs `lance-io` `providers.rs`](https://docs.rs/lance-io/latest/src/lance_io/object_store/providers.rs.html)

#### Data pages, file metadata, and scan buffers

- `CachedFileMetadata` is what the file reader caches: schema, column metadata, column infos, row count, buffer descriptors, version, and `retained_global_buffers`. `num_data_bytes` is only a count of bytes in the data-page section. `retained_global_buffers` keeps user global-buffer bytes that already fell inside the tail read on small or medium files, copied out so the larger tail allocation can be dropped. The schema buffer is not retained there. Buffers outside that window are read separately. — [docs.rs `CachedFileMetadata`](https://docs.rs/lance-file/latest/lance_file/reader/struct.CachedFileMetadata.html)
- Fragment open gets that metadata through the dataset metadata cache (`file_metadata_cache` / `FileMetadataCacheKey`) and then opens a `FileReader` with it. — [fragment.rs](https://github.com/lancedb/lance/blob/119f87b3/rust/lance/src/dataset/fragment.rs)
- The performance guide says searches “do not use a lot of memory to hold data” because they do not return much data. Scans stream, but buffer I/O. Default `io_buffer_size` is 2 GB, “enough to buffer 64 pages.” “Pages today are typically between 8 and 32 MB.” The suggested formula is up to `(2 * io_buffer_size) + (batch_size * num_compute_threads)` bytes, and `io_buffer_size` “is a soft limit” because a read cannot be smaller than one page. Default `batch_size` is 8192 rows. Local object stores use 8 I/O threads by default; cloud object stores use 64. `LANCE_IO_THREADS` overrides the count and “limits concurrent storage requests for the process.” — [Lance performance guide](https://lance.org/guide/performance/)
- A maintainer, comparing S3 with local storage, wrote that caching and buffering “don't work very differently between local and S3” and that memory use “should” be about the same. — [lancedb issue 2468](https://github.com/lancedb/lancedb/issues/2468)

#### What is not a data cache

- `ListingDatabase` stores `session: Arc<lance::session::Session>` and, when the connect request has no session, uses `Arc::new(lance::session::Session::default())`. — [docs.rs `lancedb` `listing.rs`](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)
- The session also holds `spill_store: Arc<dyn SpillStore>` created as `LocalSpillStore::default()` in `Session::new`. The sources read here do not document a byte capacity for it. — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html)
- No separate type named a runtime page cache showed up in the session, object-store, or performance-guide sources. The session documentation uses “runtime state” to mean the session itself. — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html); [Lance performance guide](https://lance.org/guide/performance/)

### Inferences

- The only durable in-process copies of table contents that these caches are designed to keep are index structures (vector partitions, B-tree pages, bitmaps) and metadata (manifests, deletion vectors, row-id structures, file and column metadata, plus global buffers that fit in the footer tail). Table data pages are read into scan/query buffers and are not a third session cache.
- Calling the registry an “object-store file cache” overstates it. It caches store clients (HTTP pools, credentials, rate limiters), one weak entry per path and parameter set. It does not cache file payloads.
- A single default session can account for about 7 GiB of cache weight (6 + 1) once both tiers fill. That weight is allowed to sit below or above RSS. Filling it does not require a leak; it requires the session to stay alive while queries touch more index and metadata.

### Gaps

- The docs.rs session source and the lance.org performance guide were both fetched as current material and do not describe the same backend or the same Session methods. Which one a given installed package matches was not tied to a release tag.
- `LocalSpillStore`’s capacity and whether it retains bytes after a request were not found.
- The pre-0.30 default entry counts were not found in a primary source. The compatibility multipliers (20 MiB and 10 MiB) are documented; the old default counts are not. LanceDB’s “default value is 256” comment is still on the entry-count setter, but current `open_table` does not pass 256 unless the caller sets the option.
- Whether `Dataset` open ignores `index_cache_size_bytes` once `ReadParams.session` is set was not confirmed in `builder.rs`. `ListingDatabase::open_table` always attaches the connection session after optionally setting the deprecated entry-count size.

## Does opening a table per request against S3 or a network filesystem leave cached pages, file handles, or metadata after the table object is garbage-collected?

### Takeaway

Dropping a table does not clear caches that live on a session the connection still holds. LanceDB keeps that session on the connection and clones it into every `open_table`. A dataset opened with its own session can drop those caches when the dataset and session are actually freed. Before a fix merged on 2025-09-10, a reference cycle in the index cache prevented that free. The object-store registry does not, in current source, keep a strong reference to a store after the last user drops it.

### Cited Findings

- LanceDB `ConnectBuilder::session` says that by default “a new session with default configuration will be created.” `ListingDatabase` stores that `Arc<Session>` on the database object. `open_table` ends with `read_params.session(self.session.clone())` before `NativeTable::open_with_params`. Tables opened from one connection therefore share the connection session. — [docs.rs `lancedb` connection docs](https://docs.rs/lancedb/latest/lancedb/connection/struct.ConnectBuilder.html); [docs.rs `lancedb` `listing.rs`](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)
- The performance guide says neither the index cache nor the metadata cache is shared between tables by default, and tells applications to keep one table or pass one session. That matches a pylance `lance.dataset()` open with no session: the dataset gets its own session. It does not match LanceDB’s connection, which injects one session for every table on that connection. — [Lance performance guide](https://lance.org/guide/performance/); [docs.rs `lancedb` `listing.rs`](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)
- A comment in `ListingDatabase::open_table` says `storage_options=None` uses “the connection's session store registry.” Passing an empty `storage_options` map “will cause a new connection to be created, and that connection will be dropped from the cache when python GCs the table object, which confounds reuse across tables.” Release of that per-table store is tied to Python GC of the table, not to an explicit cache clear. — [docs.rs `lancedb` `listing.rs`](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)
- `ListingDatabase` also keeps its own `object_store: Arc<ObjectStore>` for the database URI, obtained from `session.store_registry()`. That strong reference lasts as long as the database object. — [docs.rs `lancedb` `listing.rs`](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)
- Current registry source stores `Weak<ObjectStore>`. The registry “does not keep them alive.” A store whose last strong `Arc` is dropped can be reclaimed; the map entry is a weak pointer plus the cache key. — [docs.rs `lance-io` `providers.rs`](https://docs.rs/lance-io/latest/src/lance_io/object_store/providers.rs.html)
- Version-specific, merged 2025-09-10: “when a dataset loaded an index into its index cache, it would attach a strong reference to its index cache to the index.” “The dataset's cache contained self-referential values. This prevented the cache from getting deallocated when the dataset was dropped, resulting in a leak if many datasets were opened over time.” The fix stores a weak reference on the index. The PR is labeled `bug` and `A-python`. — [PR 4680](https://github.com/lancedb/lance/pull/4680)
- On 2025-06-26 a maintainer described a production S3 leak from “reloading SSL certificates every time we reopened an http connection to S3,” solved by reusing the store inside one session, and wrote that passing the session “was not available in our bindings” at that time. Session construction was exposed to Python and TypeScript in a PR merged 2025-07-24. That PR says the session “is attached to the Connection, and thus shared across all tables in that connection,” and deprecates table-level cache configuration. — [lancedb issue 2468](https://github.com/lancedb/lancedb/issues/2468); [lancedb PR 2530](https://github.com/lancedb/lancedb/pull/2530)
- Issue 6219 kept one session and one table alive and ran concurrent vector search against Azure. Reported `session.size_bytes` stayed around 100–147 MB while the configured caps were 100 MB each, and RSS climbed from about 0.03 GB to about 1.11 GB over roughly 420 seconds. `malloc_trim` returned on the order of 50–85 MB at each call and did not flatten RSS. A maintainer later wrote they could not reproduce it on AWS, that “the RSS is coming back after calling `trim`,” and asked whether it was Azure-specific. The issue was still open, labeled `performance`, when the page was fetched (updated 2026-08-07). — [issue 6219](https://github.com/lance-format/lance/issues/6219)
- No source read here describes a cache of open file descriptors that outlives the reader. Local vs cloud differences that are documented are `block_size` (4 KiB vs 64 KiB), I/O thread count (8 vs 64), and the cloud rate limiter. — [object store guide](https://github.com/lance-format/lance/blob/main/docs/src/guide/object_store.md); [Lance performance guide](https://lance.org/guide/performance/)

### Inferences

- “Open a table per request” has two different lifetimes. If the process also keeps the LanceDB connection, every request’s index loads and file metadata land in the connection session and stay there after the table object is collected. If each request opens a dataset or connection with a private session and then drops every reference, current code is designed to drop the index cache, metadata cache, and object store with that session, after the 2025-09-10 cycle fix.
- S3 and a network filesystem use the same session caches. What differs is the store client (HTTP client and credentials versus a file-scheme store) and the I/O thread/buffer defaults. A network mount does not bypass the index or metadata cache.
- Python dropping the table object is not the same as the cache being unmapped. The session `Arc` on the connection, a reference cycle in older builds, and glibc holding freed pages (issue 6219) can all leave RSS high after the Python object is gone.
- File-handle accumulation was not established. The long-lived objects that were established are the connection’s `ObjectStore` and the session caches, not a pool of data-page handles.

### Gaps

- The first release tag that contains PR 4680 was not identified. The merge date is 2025-09-10, which is after 0.30.0 (2025-06-19).
- It was not verified in `checkout` / `Drop` code that Python `table.close()`, deleting the table, or garbage collection runs `Drop` on the Rust dataset promptly. The listing comment only says an empty storage-options map creates a store that is dropped when Python GCs the table.
- No source was found that counts file descriptors held after a table is collected on NFS or S3.
- Issue 6219 does not say the extra RSS is the index or metadata cache. The reporter’s own cache measurement stayed near the configured cap while RSS kept rising. The cause is unresolved there.

## Are there known cases where the cache grows without a bound until the process is near its memory limit?

### Takeaway

Yes, two fixed defects let cache memory grow past the configured cap: an index-cache reference cycle when many datasets were opened, and a metadata-cache weigher that ignored the largest fields so a nominal 1 GiB cap did not evict. A separate open report shows RSS rising while the measured session cache stays inside its cap. Rotating S3 credentials have also been reported to pin cached index readers and to accumulate object-store registry entries. The default 6 GiB + 1 GiB budgets can themselves reach the 7–7.5 GB band without any of those bugs, if one session stays alive.

### Cited Findings

- Reference cycle, fixed by a commit merged 2025-09-10: opening many datasets leaked the index cache because each cached index held a strong pointer back to the cache, so dropping the dataset did not deallocate it. — [PR 4680](https://github.com/lancedb/lance/pull/4680)
- Metadata weigher, commit 2026-04-11: `CachedFileMetadata::DeepSizeOf` omitted `column_metadatas` and `column_infos`. The commit says those are the two largest fields, the weigher under-counted by about 100x (true size hundreds of KB, reported about 1 KB), and “Moka never reached the 1 GB limit, so entries accumulated indefinitely.” On a 221-million-row dataset, 30 iterations of random `ds.take()` of 64 rows grew RSS by 7,503 MB before the fix (about 250 MB per iteration, “linear, no plateau”) and by 535 MB after (about 18 MB per iteration, plateauing near 500 MB). The fix uses `prost::Message::encoded_len() * 4` as a stand-in for protobuf fields that do not implement `DeepSizeOf`. — [commit 8ac0741](https://github.com/lance-format/lance/commit/8ac0741302052ca51e0ba01827d89744f2a62fe2)
- Issue 7508, as written by the reporter, says cache keys for index metadata, manifests, and vector indexes include version or UUID, so an index rebuild inserts new entries beside old ones. The reporter says `checkout_latest` swaps the manifest and fragment bitmap and does not call `invalidate_prefix` or `clear`, and that the same under-counted `DeepSizeOf` lets a long-lived replica accumulate per-version entries until OOM. This research did not re-read `checkout_latest` to confirm the invalidation claim. The performance guide does confirm that manifest, transaction, deletion-file, and row-id keys include version, so different versions are different keys. — [issue 7508](https://github.com/lance-format/lance/issues/7508); [Lance performance guide](https://lance.org/guide/performance/)
- Issue 5658 (opened 2026-01-08, later closed): the registry key includes storage options, so refreshed S3 `access_key_id`, `secret_access_key`, and `token` create new entries. The reporter said eviction was passive and “invalid object stores remaining permanently in the cache” prevented memory from being released. The closing work is PR 10385, “prune dead entries from ObjectStoreRegistry cache, with a configurable threshold.” Current docs describe weak references plus `object_store_cache_prune_threshold` default 64. The January report and the current weak-reference source disagree about whether the store object itself stayed alive; the current docs say the registry does not hold it. — [issue 5658](https://github.com/lance-format/lance/issues/5658); [object store guide](https://github.com/lance-format/lance/blob/main/docs/src/guide/object_store.md); [docs.rs `lance-io` `providers.rs`](https://docs.rs/lance-io/latest/src/lance_io/object_store/providers.rs.html)
- Issue 7904 (closed, reporter on `lance` 8.0.0): once a vector index is cached, later dataset opens reuse cached readers bound to the `ObjectStore` from insertion time. The reporter says the Moka backend has no TTL, they observed a stale credential binding for at least 12 hours, and recovery required restarting the process that owned their session. The “process-wide” and “Session singleton” wording in that report is the reporter’s Apache Doris embedding, which creates one session and reuses it. It is not a Lance API that installs a global session. — [issue 7904](https://github.com/lance-format/lance/issues/7904)
- Issue 6219 is the unbounded-looking RSS case where the session’s measured cache did not explain the growth. Cache occupancy stayed near a 200 MB combined cap while RSS passed 1 GB. `malloc_trim` recovered only tens of megabytes. Not reproduced on AWS in the maintainer’s note. — [issue 6219](https://github.com/lance-format/lance/issues/6219)
- Issue 2468 was a single-query or few-query memory spike on S3 (about 16 GB RSS for a dataset the reporter described as about 2 GB), not a multi-day climb. The reporter was already reusing a session. A maintainer asked whether RSS grew linearly across opens. The issue was later closed and referenced by “fix: share scans across batched vector queries.” — [lancedb issue 2468](https://github.com/lancedb/lancedb/issues/2468)
- A practitioner write-up, not an upstream report, says that with `lancedb==0.25.0` the pattern of opening and closing a connection per use “causes memory leaks,” and that the author switched to one long-lived connection while still calling `open_table()` per request. The same post says an earlier context-manager close worked on `lancedb==0.21.2`. — [sprytnyk.dev production notes](https://sprytnyk.dev/posts/running-lancedb-in-production/)
- Default caps in current source are 6 GiB (index) and 1 GiB (metadata). The guide says those are the max sizes of LRU caches, and that scan buffering can add up to roughly two times `io_buffer_size` (default 2 GB) plus decode batches. — [docs.rs `lance` `dataset.rs`](https://docs.rs/lance/latest/src/lance/dataset.rs.html); [Lance performance guide](https://lance.org/guide/performance/)

### Inferences

- Two different “growth” shapes are documented. One is a session doing what it is configured to do: retain up to 6 GiB of indexes and 1 GiB of metadata for as long as the connection or session lives. Starting near 500 MB and later sitting near 7–7.5 GB is the same order of magnitude as 500 MB plus those two defaults (7 GiB is about 7.5 decimal GB). That shape should plateau once the weigher is accurate, unless scan buffers or allocator retention add more.
- The other shape does not plateau at the configured cap. The 2026-04-11 weigher bug is the one with a measured multi-gigabyte climb (about +7.5 GB in a short random-`take` test) while the cache believed it was still under 1 GB. The 2025-09-10 cycle is the one that retains a whole index cache per opened dataset after the table is dropped. Either matches a pod that approaches an 8 GB limit over a long time if the running build still has the bug. A build with both fixes and an accurate weigher should not keep every per-request session.
- Versioned cache keys mean a long-lived session can hold metadata and indexes for many dataset versions at once until the byte budget evicts them. That is bounded only when the weigher sees the real size. The 2026-04-11 commit is the evidence that, before that date, the metadata weigher did not.
- Issue 6219 is a reason not to treat a full cache as the only explanation. RSS can move up while `size_bytes` stays flat, and `malloc_trim` on Linux did not return most of it in that report.

### Gaps

- No upstream issue was found that records this specific profile (500 MB to 7–7.5 GB over 10–15 days on a network volume). The match to the default budgets and to the +7.5 GB weigher measurement is numerical, not a diagnosis of the pod.
- Release tags for the weigher fix and the cycle fix were not mapped. The dates are 2026-04-11 and 2025-09-10.
- Issue 7508’s claim that `checkout_latest` never invalidates cache prefixes was not checked in source.
- It is not known whether QuickCache, the backend in docs.rs latest `Session::new`, uses the same `DeepSizeOf` weigher the Moka bug report describes. The under-count was in `CachedFileMetadata::DeepSizeOf`, which matters for any backend that weighs by that trait.

## Which language SDKs share a process-global cache?

### Takeaway

Python, Node, and Rust do not share a process-global index or metadata cache. All three sit on the same Rust `Session`. Caches are shared only inside one process, and only among connections or datasets that were given that same `Session` instance. A LanceDB connection creates one session and shares it across tables opened from that connection. A new `connect()` or `lance.dataset()` without an explicit session gets a new session and a new object-store registry.

### Cited Findings

- `Session::default()` constructs a new `ObjectStoreRegistry::default()` each call. Nothing in that constructor installs the session into a process-wide singleton. — [docs.rs `lance` `session.rs`](https://docs.rs/lance/latest/src/lance/session.rs.html)
- Rust LanceDB: `ConnectBuilder::session` takes `Arc<Session>`. If omitted, `ListingDatabase::connect_with_options` uses `Session::default()`. Every `open_table` on that database clones that `Arc` into `ReadParams`. — [lancedb `connection.rs`](https://github.com/lancedb/lancedb/blob/main/rust/lancedb/src/connection.rs); [docs.rs `lancedb` `listing.rs`](https://docs.rs/lancedb/latest/src/lancedb/database/listing.rs.html)
- Python: `lancedb.connect(..., session=None)` documents `session` as “A session to use for this connection” that can be “re-used across multiple connections to share the same cache state.” `lancedb.Session.default()` “is equivalent to creating a session with 6GB index cache and 1GB metadata cache.” `db://` cloud connections reject `session`. — [LanceDB Python API](https://lancedb.github.io/lancedb/python/python/)
- pylance `lance.dataset(..., session=None)` documents `session` as “A session to use for this dataset. This contains the caches used by the across multiple datasets.” `index_cache_size_bytes` and `metadata_cache_size_bytes` are separate optional arguments. — [pylance dataset docs](https://lance-format.github.io/lance-python-doc/dataset.html)
- Node: `Session` in `nodejs/src/session.rs` wraps `Arc<LanceSession>`. The constructor defaults omitted sizes to `6 * 1024 * 1024 * 1024` and `1024 * 1024 * 1024` and passes `Arc::new(ObjectStoreRegistry::default())`. `Session.default()` uses `LanceSession::default()`. The class docs say sessions “can also be re-used across multiple connections to share the same cache state.” — [nodejs/src/session.rs](https://github.com/lancedb/lancedb/blob/main/nodejs/src/session.rs); [LanceDB JS Session](https://lancedb.github.io/lancedb/js/classes/Session/)
- The PR that exposed this type to Python and TypeScript says the session is attached to the connection and shared by tables of that connection. It does not describe a process-global cache. — [lancedb PR 2530](https://github.com/lancedb/lancedb/pull/2530)
- Before 2025-04-18 the object-store registry was a field on read and write params. The breaking change moved it onto the session so stores are reused by datasets that share a session and the same parameters. — [PR 3689](https://github.com/lancedb/lance/pull/3689)
- `LANCE_IO_THREADS` is process-wide, but it limits how many storage requests run at once. It is not a shared page cache. Cloud default is 64 threads; local default is 8. — [Lance performance guide](https://lance.org/guide/performance/)
- An open LanceDB issue says the Python `Session` binding “only accepts cache size parameters — the ObjectStoreRegistry is hardcoded to its default,” so Python cannot inject a custom store provider the way Rust can. That is the opposite of a hidden global registry the application can configure. Node’s constructor shown above also always builds `ObjectStoreRegistry::default()`. — [lancedb issue 3106](https://github.com/lancedb/lancedb/issues/3106); [nodejs/src/session.rs](https://github.com/lancedb/lancedb/blob/main/nodejs/src/session.rs)
- Issue 7904’s “process-wide Session” is the embedding’s own singleton (`DatasetBuilder::from_uri(...).with_session(session)` on one session kept for the process). Lance did not create that singleton. — [issue 7904](https://github.com/lance-format/lance/issues/7904)

### Inferences

- In a pod that calls `lancedb.connect()` once and `open_table()` per request, Python, Node, and Rust behave the same: one session, one registry, caches accumulate for the life of the connection up to the session budgets.
- In a pod that connects per request and drops the connection, each SDK starts a fresh session. They do not keep filling one hidden global cache. They can still leak if the build has the pre-2025-09-10 index-cache cycle, or if something else retains the connection or session.
- Separate processes never share these caches. Separate connections in one process do not either, unless the application passes the same `Session`.

### Gaps

- Java uses the same Rust core and is mentioned by the performance guide’s diagnostics section, but the Java session object was not reviewed. The question names Python, Node, and Rust only.
- No test or doc was found that measures whether two `lancedb.connect()` calls in one process accidentally alias a global registry. The constructors that were read each allocate a new registry. That is strong, but it is not an explicit “there is no global” test.
- Remote `db://` connections reject the local session. Where those server processes keep their own caches was not researched.
